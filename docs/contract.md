# `window.tmtLoader` — the hook contract (L1 + A1 + S1)

`loader/page.js` creates `window.tmtLoader` before any game script; `loader/tmt-auto.js` (a classic script, inserted
after the game's scripts, and run unchanged by the Node harness through `vm.runInThisContext`) fills in the members
below. Runners (the Playwright harness, later an embedding page) talk only to this object.

**Automation is opt-in.** The page defines `tmtLoader.automation` from `?automation=1` (the Node harness: ON by default,
`--no-automation` for the plain page) before `tmt-auto.js` runs. Without it the file stops after the contract members
— `tick`, `stateJSON`, `hash`, `pause`/`resume`, `save`, `loadFrom`, `ids`, `storage`, `profile('off')` — and adds
**no `au` layer, no DOM, nothing in `player`**, and the page does not load `games-auto/<id>.js`. The registry members
(`registerAutoFeature`, `features`, `setPolicy`, `featureState`, `hookLayer`, `hookStats`, `runtimeState`, `predicate`, `autoDerivation`, …) are then undefined, `profile()`
accepts only `off` (anything else throws), and `?profile=` / `?autoOpt=` are ignored with a console warning.

It reads the engine's globals as **bare identifiers** inside its members, never at load: `player`, `layers`, `tmp`,
`modInfo` may be global `let`s (Something Tree's `modInfo` is), which are not `window` properties.

| Member | Meaning |
|---|---|
| `id`, `manifest` | the game id (`?mod=`) and its parsed `manifests/<id>.json` |
| `ready`, `error`, `step` | `ready` turns true after `onload` (and the managed pause); any failure (a loader input that does not load, or a script's own top-level error — see `pageErrors`) sets `error = {step, message}` and shows an overlay. Poll `ready \|\| error`, never a bare timeout. |
| `automation` | `?automation=1` (docs/automation.md); `false` = contract-only mode, the rows below marked *(automation)* do not exist |
| `mobile` | `?mobile=1` (docs/mobile.md): the loader linked `loader/mobile.css` and `<html>` carries `tmt-mobile` — the single-column LAYOUT. It implies `navbar`. A layout opt-in only: it touches no `player` key, adds no layer and registers no timer, so a run with it lands on the same tick and hash as one without |
| `navbar` | `?navbar=1`, **or** `?mobile=1`, which implies it (docs/mobile.md): the loader linked `loader/navbar.css` + `loader/layerlist.css` and ran `loader/navbar.js` + `loader/layerlist.js`, and `<html>` carries `tmt-navbar` once the bar is installed. The bottom nav bar ALONE — wanted on a desktop, where the layout is not. Explicit like `mobile`, with no viewport or pointer sniffing, and the same promise about the game's state |
| `navbarUI` | *(navbar)* `{nav, refresh(), entries, seen}` — the nav bar element and what it has discovered; absent without the flag. It was `mobileUI` until `?navbar=1` split the bar from the layout |
| `layerListUI` | *(navbar)* `{panel, open(), close(), toggle(), isOpen(), refresh(), groups(), chipsOf(layer), visibleSeq(layer), cards(), expanded(), expand(layer, on), prefKey(), tip}` — the LAYER LIST the bar's first button opens (docs/mobile.md): the overlay element, its open/close, and what it is showing. Absent without the flag, and the bar hides its Layers button until it exists, so `loader/navbar.js` stands alone without `loader/layerlist.js`. PURE UI like the bar — it never writes `player`, registers no timer and adds no clickable id; its reset button and chips call the engine's own `doReset` / `buyUpgrade` / `buyBuyable` / `startChallenge` / `unlockUpg`, which is the same single click the game's own buttons make. `chipsOf` / `visibleSeq` return the components the layer's own tab layout DRAWS, in the order it draws them (docs/mobile.md, "The chips mirror the normal view"). Since U2d it also carries `countersOf(layer)` — one entry per category that layer draws, `{kind, label, mode, x, y, total, text}`, where `mode` is `ratio` (earned over drawn) or `owned` (the total held) — `actionsOf(layer)`, the chips that are unlocked and not yet bought, `fit()`, which re-measures how many buttons each row holds, and `stats()`, `{refreshes, syncs, throttled, rebuilds, fits, throttleMs}`, which is how the gate tells a throttled build from an unthrottled one. ⚠ `visibleSeq` now also yields `clickables` and `achievements`, which are COUNTED and never chipped. Since U2c it carries the three members the OPEN/CLOSED state needs: `expanded()`, the layer ids whose cards are open right now; `expand(layer, on = true)`, the chevron's own path (the class, the chevron's `aria-expanded`, the store, and the action row's re-fit on the way back) — the gate drives it through this rather than through a click, because a click is not a neutral probe; and `prefKey()`, the one `localStorage` key that state lives in, `tmt-loader:<id>:ui.layerlist.expanded`, which is the loader's OWN namespace and therefore per game. ⚠ Still nothing in `player`: the preference is a UI key beside the game's save, inside what "clear this game's save" clears (docs/mobile.md records that decision).Since U2e it carries `tip`, the TOOLTIP: `{show(el), hide(), isOpen(), el(), title(), body(), text(), key(), rich(), hoverable()}`. ONE overlay for the whole list, so opening one closes any other by construction; `title()` is the anchor's own `title` attribute read off the element (the list never recomposes the short name, so the overlay and the native tooltip cannot disagree) and `body()` is what U2e added — a declared `tooltip`, the description, the effect and the cost, composed per CATEGORY out of the fields that category's own engine component renders. `show` REFUSES an element with no layout: a collapsed card hides its chip row, and there is no box to place a tooltip against. `key()` is the component the overlay describes, `{card, role, kind, id, layer}` with `role` one of `chip` / `act` / `counter`, and it is what the overlay is re-anchored by — the action row is rebuilt when its membership moves, so the element can be replaced underneath it. `rich()` says whether the last write found anything beyond the `title`; `hoverable()` is the `(hover: none)` test that decides whether a TAP opens a tooltip, which is the device and not the width. `stats()` gains `tips`, `tipsRich` and `tipSyncs`, the last being how the gate tells a tooltip re-read on the counters' throttled path from one per animation frame. ⚠ Still nothing in `player`: the composition runs inside `withoutRaisingNaN`, because a cost or an effect string is exactly the text a TMT `format()` raises `player.hasNaN` on. Since U5 it carries two more: `chipSkin(layer)`, one entry per chip — `{key, kind, id, layer, state, skin, bg}` — where `skin` is the ENGINE's own word for the state (`bought` / `can` / `locked`, plus `pseudo` for the engines' second upgrade button) and `bg` is the colour the GAME's own stylesheet paints it, so a gate can compare the list's answer against one it rebuilt itself; and `cameFrom()`, the layer tab this list opened, for as long as it is still the tab on screen — `null` for one opened from the tree. ⛔ `cameFrom` is SESSION-ONLY and read-only: still nothing in `player`, and — unlike the expander's preference — nothing in storage either (docs/mobile.md records the decision). The list never swallows the engine's own back handler; it opens the overlay over whatever that handler navigated to. Since U6 the COLLAPSED card carries colour too: an ACTION BUTTON wears its chip's skin (`data-skin` beside the `data-afford` it already had — two different questions, "what IS this" and "can I press it now"), and every COUNTER wears the user's own three-way rule, exposed as `counterSkin(layer)`: one entry per counter, `{kind, mode, x, y, text, available, skin, bg}`, where `available` is "is there anything to do in this category right now" and `skin` is `bought` (the category is finished) / `can` (there is) / `locked` (there is not) — docs/mobile.md has the table, and challenges and clickables in it are an INFERENCE rather than a ruling. ⚖ And since U6 pressing an INACCESSIBLE layer does nothing at all: the list asks the ENGINE's own `layerunlocked` (falling back to `player[l].unlocked`) BEFORE it hides itself, so a refusal leaves the overlay open, `player.tab` where it was and `cameFrom` untouched. Since U7 it carries three more readers, all of them REPORTING what the card renders rather than a second reading of it: `resetLines(layer)`, the engine's prestige string split on its FIRST run of `<br>`s into the two rows the card gives its own line boxes (⚖ the user's "always two lines"; a string with no break at all leaves the second empty, and it still occupies its row — the reservation is never keyed on the second being non-empty, because the `normal` prestige text DROPS its whole second half once `resetGain` passes 100); `resources(layer)` and `resourceText(layer)`, the layer's OTHER resources — every Decimal in `player[layer]` the engine did not put there whose value the layer's own display text states, `{layer, key, text, collide}` with the player KEY as the label, and the text they were detected in, which is what a caller lifts a prose label out of. ⛔ The text comes from the DECLARATION, not `tmp` — the engines only evaluate a layer's `tabFormat` / `display` / `description` members into `tmp` while THAT layer's tab is open — so this reader CALLS the game's own display functions, guarded, once per card per 250 ms sync; ⚠ it is therefore the most likely thing in this file to break the "writes nothing to `player`" claim, and gate M1 asserts the state hash across a full render rather than assuming it. And `progress(layer)`, `{rows, dropped}`: one row per category the card DRAWS that has a numeric target and something unearned in it — `{kind, layer, id, label, name, how, candidates, currency, have, need, text}` — where `how` is `cheapest` (a cost exists and every candidate's currency agrees), `first` (they do not, so the first-listed wins — ⚖ the user's own fallback) or `only`. Milestones, achievements and clickables declare no number at all and get no row. `dropped` names what was passed over and why: `multiRes` (a cost in several currencies at once, where `cost` itself is undefined) and `currency` (the engine says the component CAN be bought while the engines' own generic amount reader says it is short — the tell for a game that buys with something it never declared). Since U8 a resource row, once shown, STAYS shown: `resources(layer)` gains `sticky` (this row is standing on the MEMORY, because the layer's text states nothing claimable for it right now) and `claimed` (the occurrence it took out of the prose, or `null`), and the printed `text` is now OURS — `format(value)` for EVERY row, attributed or remembered, so a row cannot change its own string at the instant of a reset (the two formatters disagree for a non-zero value under 1,000; `format` is the one that does not ROUND a fractional resource). ⛔ Only an UNAMBIGUOUS sighting is remembered — a key shown with `collide === false` — because the attribution between two keys that claimed the same printed number is by `player[layer]` key order alone. The memory is `resourceMemory()`, `{layer: [key, …]}`, and `forgetResources()` clears it (the cache AND the stored key; it deliberately does NOT re-render, so a caller can watch the next render fill it again). ⚠ Still nothing in `player`: it is one `storage.raw` key in the loader's own namespace, `tmt-loader:<id>:ui.layerlist.resources`, beside the expander's — inside what "clear this game's save" clears, which is why a cleared game correctly comes back having forgotten which rows it had shown |
| `flags` | `{mobile, navbar, automation}` — the three opt-ins AS RESOLVED (docs/options.md), the same values as `mobile` / `navbar` / `automation` beside them. Each is answered by the URL parameter when the URL says anything at all about it (`?mobile=1` **and** `?mobile=0` both answer), and otherwise by the one remembered preference the Options section writes. Nothing else can set one: there is no viewport or pointer sniffing anywhere, and a page with neither a parameter nor a preference is the page the loader has always served |
| `flagSource` | per flag, WHO answered: `url` \| `stored` \| `implied` \| `default`. `implied` is the bar under `?mobile=1`, which has always implied it. The Options section reads this to say, in the panel, that the address is currently overriding what this browser remembers |
| `prefs` | `{key, names, read(), write(prefs)}` — the remembered choice. ONE key for every game, `tmt-loader:ui.flags`, deliberately NOT under `tmt-loader:<id>:`: these say what kind of device and session the person wants, and the per-game namespace is what the picker's "clear this game's save" deletes (docs/options.md records the decision). Read and written through the RAW `Storage` methods, captured before `installSavePrefix()` patches the prototype; every read and write is wrapped, so a blocked or full store costs the preference and never the page. `write()` returns what is stored afterwards; only the flags that are ON are written, and the key is removed when that is none of them |
| `optionsUI` | `{id, entries, section(), button(flag), refresh(), press(flag), anchor()}` — the OPTIONS SECTION (docs/options.md), the loader's own three buttons inside the game's own options tab. `loader/options.js` is the one loader file inserted with NO flag in front of it, because a page carrying none of the flags is the page that needs to offer them; what it costs an untouched page is one `<div>` inside the options tab while that tab is open, and nothing else — no `<head>` entry, nothing in `player`, no timer, no request. PURE UI, like the bar and the list. It knows no tab id: it anchors on the game's own `<button class="opt" onclick="hardReset()">` and takes `#optionWheel`'s absence as that engine saying the options tab is open (both censused over the roster by `tools/census-figures.mjs`). A press writes the preference, drops that flag's parameter from the address and RELOADS — every one of these flags needs a reload, and a toggle that looked pressed and changed nothing is the one unacceptable answer |
| `managed` | `?managed=1`: the loader calls `pause()` right after `onload`; the runner drives `tick()` |
| `plan`, `loaded`, `modFiles` | the `interpret()` plan, the files executed in order (skipped files are not in it), the modFiles paths |
| `skipped` | manifest-relative paths of game scripts (static or modFiles) that **failed to load and were skipped**, in order; one `console.warn` each. A browser skips a `<script src>` that 404s and keeps going, so the loader does too. The loader's own inputs — the manifest, `index.html`, `loader.js`'s source, a vendored file, `loader/tmt-auto.js`, `games-auto/<id>.js` — still fail the load. Gate G1 allows a skip only for a path in the manifest's `load.known.missingScripts` (docs/manifest.md) |
| `pageErrors` | every uncaught error that reaches `window`, as `{when: 'before-ready' \| 'after-ready', message, filename}`, appended as they happen. **Attribution rule:** while a script is being inserted, only an error whose `ev.filename` equals that script's resolved `src` (an inline script: the document URL) is the script's own and fails the load (overlay, `error`). Errors from a game's timers, earlier scripts or Vue do not fail the load; they are recorded here. G1 allows `before-ready` entries only when `load.known.errorsBeforeReady` is declared, and `after-ready` entries never |
| `pause()` / `resume()` | stop / restart every `setInterval` the timer recorder saw (game loop, autosave, canvas flag, component timers). Interval ids are logical and survive a pause, so a later `clearInterval(id)` still works. Timeouts and animation frames are counted, not paused. |
| `timers` | `{paused, counts, list()}` |
| `tick(diff, n = 1)` | `n` × (`updateTemp(); gameLoop(diff); fixNaNs?.()`) — the census/probe loop; returns `{ticks, gameSeconds}` |
| `ticks`, `gameSeconds` | counters owned by `tick()`; reset by a page load |
| `stateJSON(opts)` | `JSON.stringify(player)` without keys named `time` / `offTime` at any depth, plus `manifest.headless.stateMask`; `opts.exclude` = top-level `player` keys to drop (`['au']` compares against a pre-A1 anchor). ⛔ **Excluding a LAYER also drops `player.subtabs[<that layer>]`** — the engines keep which subtab of a layer's tab is on screen in a separate top-level key, so a caller that drops `au` and not `subtabs.au` asks for "the game without the automation layer" and gets the automation layer's view state anyway. V1 learned this the expensive way: `hashGame` had the subtabs exclusion and `--exclude au` did not, and the moment the `au` tab took subtabs all eight L1 anchor rows of `gates-a1 --part 2` went red (ptr idle 1000: `86067be644ce481c` → `51c48535df82cc29`) while `hashGame` was untouched. Two spellings of one intention; there is now one |
| `gameState`, `hashGame()` | **ONE definition of "the GAME's state"** — what the harness calls `hashGame` — and every consumer reads it from here rather than repeating the literal (`tools/harness/boot.mjs` for a mark's captured JSON and for the live state, `loader/tmt-planner.js`, `tools/harness/upstream-export.mjs`). It excludes the `au` layer, and by the rule above the au tab's selected subtab with it: **`player.au`**, the loader's own side layer, whose `clickables` map has one key per toggle BUTTON so the full hash moves with the NUMBER of registered features; and **`player.subtabs.au`**, which the engines write when the `au` tab took subtabs in V1 (`{mainTabs: "Simple"}` at `getStartPlayer`, re-added to an imported save by `fixData`, measured on both). Without the second line every pinned `hashGame` in the repo would have moved, and a PLAYER switching subtab would move it again mid-run: the au tab's VIEW state is not game state. ⚠ Measured before the change, on both engines: `player.subtabs.au` was **absent**, so deleting the key reproduces the historical bytes exactly (deletion does not reorder what is left) — the open question "2.7 may already write `subtabs.au = {}`" is answered, it does not |
| `hash(opts)` | Promise of the first 16 hex of sha256(`stateJSON(opts)`) — `crypto.subtle` in the page, `node:crypto` in Node (injected as `sha256hex`); equal by gate G3 |
| `save()` | the game's own `save()` with **no argument**; returns `storage.list()` |
| `loadFrom(json)` | `importSave(btoa(json), true)` — the game's own import. **Both engines then reload the page**; the import completes on the next `ready`. In Node the harness boots a fresh process on the storage `importSave` wrote. |
| `ids()` | `{layers: {id: {row, type}}, ids: ["<layer>:<ms\|upg\|buy\|ch\|ach>:<id>"], counts}` — numeric ids only (the census rule); layers the loader adds (`au`, flagged `tmtLoaderLayer`) are left out |
| `profile(name)` | *(automation)* `off` \| `all` \| `saved`; contract-only: `off` only (docs/automation.md); no argument returns the current one. The page applies `?profile=` after `onload` (default `off` when managed, else `saved`); the Node harness `--profile` (default `off`) |

| `features` | *(automation)* the registered features, in layer order × kind order — DERIVED from each tree layer's declarations (`toggles` / `upgrades` / `buyables` / `challenges` / `clickables` / `reset`) and shaped by `autoTable` |
